# Team Builder

設計書やタスクリストに基づいてエージェントチームを構築し、並列実装とコードレビューを行う Claude Skill。
技術ドメインで作業を分割し、依存関係を管理する。

## 何ができるか

- 設計書・タスクリストからエージェントチームを自動構築
- 技術ドメイン（バックエンド / フロントエンド / インフラ等）でタスクを分割
- 独立タスクの並列実行で実装を高速化
- 実装完了後に自動でコードレビューを実施
- レビュー指摘をリーダーが一括修正

## こんな時に使える

`/team-builder` の発動条件（全て YES なら使う）:

⬛ MUST

- [ ] 1 つの feature/PR スコープ内に独立タスクが 3 個以上ある
- [ ] 各タスクが**異なるファイル**を編集する（同一ファイルなし）
- [ ] 順次依存ではなく並列化で短縮できる
- [ ] 各タスクが 1〜3 ファイル程度に収まる

典型的なトリガー入力例:

- 「この設計書に沿って実装して」
- 「フロントとバックを同時に直して」
- 「N 個のサービスを並行リファクタしたい」
- 「セキュリティ / パフォーマンス / テスト観点でそれぞれレビューして」

## 使わない方がいいケース

- タスクが 1〜2 個で並列化の効果が薄い
- 単一ドメインの小規模な変更
- 順次依存が多く直列化せざるを得ない作業
- 同一ファイルを複数エージェントが編集する必要がある（**上書きによるデータ消失**）
- コスト感度が高い場合（単一セッションの数倍のトークンを消費）
- 研究・調査のみのタスク

### `/team-builder` vs. 新しい cmux ウィンドウを開く

cmux で「タスクごとにウィンドウを変える」ワークフローと両立する。住み分けは:

| cmux ウィンドウを開く | `/team-builder` を呼ぶ |
|----------------------|----------------------|
| 別 feature / 別ブランチ | 1 つの feature 内に複数成果物 |
| 各タスクで深い対話が必要 | 仕様が明確で fan-out 可能 |
| 長時間の探索作業 | 予測可能な実装作業 |
| 別リポ / 別 cwd | 同一リポ・同一ブランチ |

通常は cmux ウィンドウ単位で十分。発動条件が揃った時だけ `/team-builder` を呼ぶ。

## 使い方

### 1. スキルを呼び出す

```
/team-builder
```

設計書やタスクの内容を伝えると、まず**ドライランプラン**を提示する。

### 2. 実行の流れ

```
1. 発動条件チェック
   ↓
2. ドライランプラン提示 → ユーザー承認待ち
   ↓ (承認後)
3. TeamCreate + TaskCreate + 依存関係設定
   ↓
4. 実装エージェント並列起動
   ↓
5. 全実装完了 → レビュワー起動
   ↓
6. レビュー指摘をリーダーが修正
   ↓
7. クリーンアップ（agents / Team）
```

cmux 環境では、`Running` / `Needs input` のステータスピル表示は cmux Claude wrapper が自動で行う（このスキルはサイドバー状態を一切触らない）。

### 3. ドライランプラン（必須）

`/team-builder` 起動時、エージェントを起動する前に必ず以下を提示してユーザー承認を取る:

- タスク表（# / role / subject / files）
- ファイル所有権マップ
- 依存関係
- モデル戦略 + コストクラス（low / medium / high）

承認後に初めて `TeamCreate` に進む。

### 4. モデル戦略

| 戦略 | リーダー | 実装担当 | レビュワー | 用途 |
|------|---------|---------|-----------|------|
| **adaptive**（推奨） | opus | sonnet | opus | 通常の開発 |
| **deep** | opus | opus | opus | 複雑な設計、セキュリティ重要 |
| **fast** | sonnet | sonnet | sonnet | 速度重視、定型作業 |
| **budget** | sonnet | haiku | sonnet | コスト最小化 |

## チーム構成パターン

### パターン 1: フルスタック機能

```
backend-dev (sonnet)  → API コントローラー、モデル、マイグレーション
frontend-dev (sonnet) → ページ、コンポーネント、API フック
infra-dev (sonnet)    → IaC 定義、IAM ポリシー、環境設定
reviewer (opus)       → 全体レビュー
```

### パターン 2: API + データベース

```
schema-dev (sonnet)   → マイグレーション、モデル定義、シードデータ
api-dev (sonnet)      → コントローラー、ユースケース、スキーマ
test-dev (sonnet)     → 統合テスト、ユニットテスト
reviewer (opus)       → 全体レビュー
```

### パターン 3: リファクタリング

```
refactor-a (sonnet) → サービス A 側のファイル群
refactor-b (sonnet) → サービス B 側のファイル群
reviewer (sonnet)   → 全体レビュー
```

### パターン 4: 並列レビュー・調査

```
security-reviewer (opus)    → セキュリティ観点
performance-reviewer (opus) → パフォーマンス観点
test-reviewer (opus)        → テストカバレッジ観点
```

## 重要なルール

| ルール | 理由 |
|--------|------|
| ドライランプランは必須 | 起動前にユーザー承認を取ることでムダな起動を防ぐ |
| 同一ファイルの並行編集禁止 | 後から書き込んだ方が先の変更を無言で上書きする |
| エージェント数は 3〜4 が最適 | 多すぎると調整コスト増、少なすぎると並列効果薄 |
| レビューは全実装完了後 | 途中レビューは手戻りが増えるだけ |
| レビュー修正はリーダーが担当 | エージェント再起動のオーバーヘッドを避ける |
| プロンプトに全情報を含める | エージェントは独立セッションで動く |

## ファイル構成

```
team-builder/
├── SKILL.md     # Claude 向け指示書（英語）
└── README.md    # このファイル（日本語解説）
```

## 前提条件

- Claude Code のチーム機能（TeamCreate, Task tools, SendMessage）が利用可能
- 並列化の効果がある程度ある規模のタスク（3 タスク以上推奨）
