# 既存コメント確認のルール

PR に付いている未解決のレビュースレッドについて、指摘への対応が適切かを判定する。新しい問題を探すのではなく、すでに出ている指摘の対応状況だけを見る。

## 作業手順

1. スレッドごとに、最初のコメント（指摘）と、それ以降の返信をすべて読む。
2. 指摘の内容を 1 文で要約する。
3. 指摘のあとに作られたコミットを、コミット一覧の日時で特定する。
4. 該当ファイルの現在のコードを Read で読む。`isOutdated` が `true` の場合は行番号がずれているので、`originalLine` と指摘の内容から該当箇所を探す。
5. 必要に応じて、指摘のあとのコミットの差分を `git show <ハッシュ> -- <パス>` で確認する。
6. 下の判定基準で、スレッドを 1 つの判定に分類する。
7. 判定の理由を、見たコミットやコードを挙げて 1〜3 行で書く。

## 判定基準

| 判定 | 条件 |
| --- | --- |
| 未対応 | 指摘のあとに該当箇所の変更がなく、返信もない。 |
| 対応が不十分 | 該当箇所は変更されたが、指摘の一部しか解消していない。または、変更によって別の問題が生じている。 |
| 説明の再確認が必要 | コードは変えずに返信で説明しているが、その説明が指摘の懸念に答えていない。または、説明の内容がコードと食い違っている。 |
| 対応済み（解決してよさそう） | コードの変更で指摘が解消している。または、返信の説明が妥当で、コードの変更が不要だと判断できる。 |

⬛ MUST

- `isOutdated` が `true` であることだけを理由に、対応済みと判定しない。行が変わっただけで、指摘が解消していないことがある。
- 判定の根拠には、現在のコードを Read で確認した結果を使う。返信に「直しました」と書かれていても、コードで確認できなければ対応済みにしない。
- 指摘自体の妥当性は評価しない。指摘が誤っていると考える場合は、判定を「説明の再確認が必要」にして、理由にその旨を書く。

◆ SHOULD

- 質問のコメント（`[ASK]` など）は、返信で回答されていれば対応済みとする。
- 軽微な指摘（`[NITS]` など）で、返信で「対応しない」と合意されているものは対応済みとする。

## 出力フォーマット

スレッドごとに、以下の形式で返す。順番は「未対応」→「対応が不十分」→「説明の再確認が必要」→「対応済み」とする。

```markdown
**1. [判定] 指摘の要旨**
📍 `ファイルパス:行番号` ・ {スレッドの URL}

判定の理由（1〜3 行）

---
```

- 行番号には、現在のコードでの位置を書く。現在の位置を特定できない場合は、`originalLine` を書いて「（元の位置）」と添える。
- コメントの投稿者の名前は出力しない。スレッドの URL で参照できるようにする。
