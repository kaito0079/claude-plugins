# セキュリティ観点のルール

変更がセキュリティ上の新しいリスクを持ち込んでいないかを確認する。観点名は `セキュリティ` と書く。

## 作業手順

1. 変更の目的（WHY）を理解する。
2. 差分を読み、変更されたファイルと内容を把握する。
3. 変更ファイルの全体を Read で読み、差分の前後の文脈を理解する。
4. 必要に応じて、ルーティング、認証・認可の設定、データモデルなどの関連ファイルも確認する。
5. プロジェクトの規約文書にセキュリティのルールがあれば、それを読んで根拠にする。
6. 指摘候補を挙げ、対象のコードが実際に存在するかを Read で確認する。確認できない候補は除外する。
7. 候補ごとに、今回起因か既存負債かを判定する。
8. 共通基準の出力フォーマットで結果を返す。

## チェックポイント

### インジェクション

- 外部入力が、エスケープやパラメータ化なしに SQL、シェルコマンド、HTML、テンプレートに渡っていないか。
- ファイルパスや URL を外部入力から組み立てる箇所で、パストラバーサルや SSRF の対策があるか。

### 認証・認可

- 新しいエンドポイントや操作に、認証と認可のチェックが入っているか。
- 他のユーザーやテナントのリソースに、ID の差し替えだけでアクセスできないか。
- プロジェクトが採用している既存の認可の仕組みを迂回していないか。

### データの保護

- パスワード、トークン、個人情報などが、ログやレスポンスやエラーメッセージに出ていないか。
- 秘密情報がコードや設定ファイルにハードコードされていないか。
- リクエストのデータを、更新を許可する項目で絞り込まずにそのまま保存処理へ渡していないか（Mass Assignment）。

### セッションとリクエスト

- 状態を変更する操作に、CSRF などの対策があるか。
- Cookie やセッションの属性が、既存の設定より弱くなっていないか。

### 依存関係

- 新しく追加した依存パッケージが、プロジェクトの目的に対して妥当か。
- ロックファイルの変更に、意図しない依存の追加や更新が含まれていないか。

## 担当外

- セキュリティに関係しないバグは、`ロジック` の観点が担当する。
