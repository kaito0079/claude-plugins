# ロジック観点のルール

変更の正確さと、データや処理の整合性を確認する。観点名は `ロジック` と書く。

## 作業手順

1. 変更の目的（WHY）を理解する。
2. 差分を読み、変更されたファイルと内容を把握する。
3. 変更ファイルの全体を Read で読み、差分の前後の文脈を理解する。
4. 必要に応じて、呼び出し元、型定義、テストなどの関連ファイルも確認する。
5. 指摘候補を挙げる。この段階では仮説でよい。
6. 候補ごとに、対象のコードが実際に存在するかを Read で確認する。確認できない候補は除外する。
7. 候補ごとに、今回起因か既存負債かを判定する。
8. 共通基準の出力フォーマットで結果を返す。

## チェックポイント

### 目的との整合

- 変更が WHY に書かれた目的を実際に達成しているか。
- 目的に関係のない変更が紛れ込んでいないか。

### 影響範囲

- 変更した関数、型、スキーマの呼び出し元や利用箇所が、すべて追従しているか。
- インターフェースや返り値の形を変えた場合に、利用側が壊れていないか。

### データの整合性

- 複数の書き込みが、必要な単位でトランザクションなどにまとめられているか。
- 同時実行や同時更新が起こりうる箇所で、競合への対策があるか。
- 削除や更新が、関連するデータに意図しない影響を与えないか。

### エッジケース

- null、未定義、空配列、空文字列が安全に扱われているか。
- 境界値（0、上限、最大長、日付の範囲など）で正しく動くか。
- 型の不一致（文字列と数値の比較、タイムゾーンを含む日付の扱いなど）がないか。
- エラーや例外が握りつぶされず、適切に扱われているか。

### 処理の効率

- ループの中でのクエリ発行（N+1）など、明らかに非効率な処理がないか。
- 同じデータを何度も取得していないか。

### 構造

- プロジェクトの既存のレイヤー構造や依存の向きに反していないか。規約文書があれば、それを根拠にする。

## 担当外

- 設計や可読性の改善提案は、`改善提案` の観点が担当する。
- プロジェクト規約への準拠は、`規約準拠` の観点が担当する。
