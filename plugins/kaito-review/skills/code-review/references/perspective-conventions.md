# 規約準拠観点のルール

プロジェクト固有の規約とパターンに、変更が沿っているかを確認する。観点名は `規約準拠` と書く。

ほかの観点がコードの品質を見るのに対して、この観点はプロジェクトの規約文書への準拠だけを見る。

## 作業手順

1. プロンプトで渡された規約文書のうち、変更ファイルの種類（言語、レイヤー、ディレクトリ）に関係するものを Read で読む。
2. 差分を読み、変更されたファイルと内容を把握する。
3. 変更ファイルの全体と、同じディレクトリにある既存ファイルを Read で読み、既存のパターンを把握する。
4. 規約文書の記述と変更内容を突き合わせ、指摘候補を挙げる。
5. 候補ごとに、対象のコードが実際に存在するかを Read で確認する。確認できない候補は除外する。
6. 共通基準の出力フォーマットで結果を返す。

## 指摘の書き方

⬛ MUST

- 指摘には、根拠にした規約文書のファイル名と節を必ず書く。
- 例: 「`CONTRIBUTING.md` の命名規則の節ではフックに `use` プレフィックスを付けるとありますが、ここでは付いていないようです。」
- 規約文書に書かれていない事項は指摘しない。

## チェックポイント

規約文書に書かれている範囲で、以下を確認する。

- ディレクトリ構成とファイルの置き場所。
- 命名規則。
- レイヤー構造と、層の責務の分け方。
- 使うことが決まっているライブラリや実装パターン。
- API 仕様書やスキーマ定義など、コードと一緒に更新すると決まっている成果物の更新漏れ。
- 行の長さやファイル終端の改行など、コーディング標準。

## 指摘しないこと

- 今回の変更で触れていない箇所の規約違反。
- 設計改善の提案。これは `改善提案` の観点が担当する。
- 規約とは関係のないバグ。これは `ロジック` の観点が担当する。
