# テスト観点のルール

変更に対するテストの有無と質を確認する。観点名は `テスト` と書く。

## 作業手順

1. 変更の目的（WHY）を理解する。
2. 差分を読み、変更されたファイルと内容を把握する。
3. 変更されたコードに対応するテストファイルを探して Read で読む。
4. プロジェクトのテストの慣例を確認する。変更箇所と同じ領域に既存のテストがあるか、テストの置き場所と書き方がどうなっているかを見る。
5. 指摘候補を挙げ、対象のコードが実際に存在するかを Read で確認する。確認できない候補は除外する。
6. 候補ごとに、今回起因か既存負債かを判定する。
7. 共通基準の出力フォーマットで結果を返す。

## 適用範囲

⬛ MUST

- テストが書かれていない領域（たとえば特定のディレクトリやレイヤーにテストが 1 件もないなど）では、テストの追加を求める指摘をしない。テストを書かない運用が確立した慣例である可能性が高いためである。
- 判断の根拠として、その領域に既存のテストがあるかどうかを確認する。

## チェックポイント

### テストの存在

- ビジネスロジックの変更に、テストの追加や更新が伴っているか。
- テストが、プロジェクトの慣例どおりの場所に置かれているか。

### テストの網羅性

- 正常系だけでなく、異常系（バリデーションエラー、存在しないリソース、権限エラーなど）も確認しているか。
- 境界値（数値の上限と下限、最大長、日付の範囲など）を確認しているか。
- 修正したバグについて、再発を防ぐテストがあるか。

### テストの質

- アサーションが具体的か。常に成功するアサーションになっていないか。
- テストデータが、特定の ID や環境に依存していないか。
- モックの範囲が適切か。テスト対象そのものをモックしていないか。

### テストの独立性

- テスト同士がデータや実行順序に依存していないか。
- 外部サービスや時刻に依存せず、CI で安定して実行できるか。

## 担当外

- テスト以外のコードのバグは、`ロジック` の観点が担当する。
