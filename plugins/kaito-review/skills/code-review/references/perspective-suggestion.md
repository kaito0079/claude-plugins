# 改善提案観点のルール

問題を検出するのではなく、コードをより良くする提案をする。観点名は `改善提案` と書く。

## 出力タグ

⬛ MUST

- 出力するタグは、原則として `[IMO]` か `[NITS]` にする。
- `[MUST]` は使わない。

## 作業手順

1. 変更の目的（WHY）を理解する。
2. 差分を読み、変更されたファイルと内容を把握する。
3. 変更ファイルの全体を Read で読み、周辺の既存コードのパターンを把握する。
4. 指摘候補を挙げ、対象のコードが実際に存在するかを Read で確認する。確認できない候補は除外する。
5. 共通基準の出力フォーマットで結果を返す。

## チェックポイント

### 既存パターンとの一貫性

- 同じ種類の処理について、リポジトリ内の既存コードと書き方がそろっているか。
- 既存のユーティリティや共通部品で置き換えられる、新しい実装がないか。

### 可読性

- Early Return などで、ネストを浅くできないか。
- 変数名や関数名が、処理の意図を表しているか。
- 複雑な条件式を、意図を表す名前の変数や関数に抽出できないか。

### パフォーマンス

- ループの中で、毎回同じ処理を繰り返していないか。
- フロントエンドであれば、不要な再レンダリングや再計算が起きていないか。

### 共通化

- 変更箇所に、既存コードとの重複がないか。
- ただし、無理に共通化しない。2 か所程度の類似であれば、個別に実装したほうがよい場合もある。

## 担当外

- バグや不整合は、`ロジック` の観点が担当する。
- プロジェクトの規約違反は、`規約準拠` の観点が担当する。
