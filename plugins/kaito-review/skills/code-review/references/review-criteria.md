# レビュー共通基準

すべての観点のレビュアーが共通で守るルールを定義する。

## レビューの観点

以下の 3 点を軸にレビューする。

1. **WHY との整合性:** 変更の目的に対して、変更が適切に対応しているか。
2. **影響範囲のカバー:** 変更によって影響を受ける箇所が、漏れなく対応されているか。
3. **品質:** 変更自体に、バグ、セキュリティの問題、設計上の問題がないか。

## 検証の絶対ルール

⬛ MUST

1. **実コードを確認する。** 指摘する前に、該当コードを Read で読んで実装を確認する。差分だけでなく、呼び出し元、型定義、バリデーション、テストなどの関連コードも確認する。
2. **仮説だけで指摘しない。** 「〜の可能性がある」だけで根拠を示せない指摘は出さない。指摘には、ファイルパス、行番号、実際のコードの引用を含める。
3. **スコープを守る。** 変更されていないコードには指摘しない。ただし、変更が既存コードに影響する場合は、その関連を明示したうえで言及してよい。
4. **一般論を根拠にしない。** 「ベストプラクティスだから」だけを根拠にしない。プロジェクトの規約文書や既存コードのパターンなど、具体的な根拠を示す。

## 指摘の分類

各指摘の本文の先頭に、以下のどちらかを 1 行付ける。

| 分類 | 意味 | タグの扱い |
| --- | --- | --- |
| `> 今回起因` | この変更で新たに導入された問題や提案 | すべてのタグを使える |
| `> 既存負債` | 変更前から存在していた問題 | `[MUST]` は使わず、`[IMO]` 以下に落とす |

既存の問題であっても、今回の変更で顕在化した場合や悪化した場合は、`> 今回起因` として扱ってよい。

## 指摘しないこと

- 今回の変更で導入されたものではない、既存の技術的負債。
- 変更の範囲を超えた、大規模なリファクタリングの提案や設計の全面的な否定。
- プロジェクトの既存の慣例やパターンに沿った書き方。慣例と異なる書き方を提案したい場合でも、重要度は下げる。

## 重要度タグ

| タグ | 意味 | 使い方 |
| --- | --- | --- |
| `[MUST]` | 修正必須 | バグ、セキュリティ脆弱性、データ不整合など、マージ前に対応が必要なもの |
| `[IMO]` | 改善推奨 | 設計改善やパフォーマンス向上など、議論したうえで判断するもの |
| `[NITS]` | 軽微 | 命名や可読性の改善など、対応が任意のもの |
| `[ASK]` | 質問・確認 | 実装意図や仕様の確認など、回答を求めるもの |
| `[LGTM]` | 良い実装 | 良い設計判断、丁寧なテスト、工夫された実装への肯定的な評価 |

### タグの使い分け

- `[MUST]` は、本当にマージを止めるべき問題にだけ使う。
- `[MUST]` にするか迷ったら `[IMO]` を使い、判断をレビュアーに委ねる。
- `[LGTM]` も積極的に使う。良い点を明示すると、レビューの質が上がる。
- 指摘はそのまま PR に転記されることを想定し、質と量を吟味する。

## 出力のトーン

- やわらかい表現を使う。「〜してはいけない」ではなく「〜しておくと安心です」と書く。
- 断定的な否定を避ける。「間違っています」ではなく「こうすると良さそうです」と書く。
- 提案として伝える。「〜すべき」ではなく「〜を検討してもよいかもしれません」と書く。
- 良い点は素直に褒める。

## 出力フォーマット

指摘は以下の形式で返す。親のスキルが統合に使う。

```markdown
### [タグ] (N件)

**1. [観点] 簡潔な問題タイトル**
`ファイルパス:行番号`
> 今回起因

本文（3〜5 行を目安に、状況の説明と提案を自然な流れで書く）

---
```

- 指摘と指摘の間は `---` で区切る。
- ファイルパスと行番号は、本文とは別の行にバッククォートで書く。
- 問題が複数行にまたがる場合は、`ファイルパス:開始行-終了行` の形で範囲を示す。
- コード例が必要な場合は、1〜3 行に収める。
- 指摘が 1 件もない場合は、そのことを 1 行で返す。

## 他観点での気づき（任意）

担当観点の作業中に、別の観点が担当する事項に気づいた場合は、捨てずに結果の末尾に以下のセクションを追加する。親のスキルがこれを受け取り、担当の観点を追加起動して検証する。

```markdown
### 他観点での気づき

**1. [推定カテゴリ] タイトル**
`ファイルパス:行番号`

担当外であることを冒頭に書いたうえで、なぜ気になったかを 1〜3 行で書く。
```

- **探しに行かない。** 担当観点の作業中に、ついでに目に入ったものだけを書く。他の観点のために追加の Read や Grep をしない。
- **根拠のないものは書かない。** コード片やファイルパスなど、具体的な根拠を示せるものだけを書く。
- 仮説でかまわない。検証は担当の観点が後から行う。タグは付けない。
- 推定カテゴリは、`ロジック` / `セキュリティ` / `テスト` / `改善提案` / `規約準拠` のどれかにする。
