# PR レビュー スキル

変更差分に対して、観点別のサブエージェントを並列に起動してレビューを実行する。

## ゴール

レビュアーがすぐにアクションを取れる形で、差分に対する指摘を `[MUST]` / `[IMO]` / `[ASK]` / `[NITS]` / `[LGTM]` のタグ付きでまとめて提示する。

## 完了条件

1. 常時起動の 4 観点と、条件を満たした場合の規約準拠観点の結果が、すべて統合されて表示されている。
2. 各サブエージェントが報告した「他観点での気づき」が検証され、結果が統合されている。
3. すべての指摘が `references/review-criteria.md` の出力フォーマット（タグ・分類・ファイルパス・本文）を満たしている。
4. 同じ `ファイル:行番号` への重複指摘が 1 件にマージされている。
5. PR モードで未解決のレビュースレッドがある場合は、すべてのスレッドの対応状況が判定され、表示されている。
6. 既存スレッドと同じ内容の新規指摘が、二重に出ていない。
7. 差分が空の場合は、その旨を伝えて終了している。

## Step 1: 差分の取得

以下の優先順で差分ソースを決定する。

**1. `$ARGUMENTS` に PR 番号（`123`、`#123`、`PR #123` など）がある場合は、指定番号の PR モードで処理する。**

```bash
gh pr view <PR番号> --json number,title,body,author,baseRefName,additions,deletions,changedFiles
gh pr diff <PR番号>
gh pr diff <PR番号> --name-only
```

**2. `$ARGUMENTS` がない場合は、現在のブランチに紐づく PR を自動検出する。**

```bash
gh pr view --json number,title,body,author,baseRefName,additions,deletions,changedFiles
gh pr diff
gh pr diff --name-only
```

成功したら PR モードで処理する。`gh` が使えない場合や、現在のブランチに PR がない場合は 3 に進む。

**3. PR がない場合は、ローカル差分モードで処理する。**

```bash
git symbolic-ref refs/remotes/origin/HEAD | sed 's@^refs/remotes/origin/@@'
git diff <base>...HEAD
git diff <base>...HEAD --name-only
git log <base>...HEAD --oneline
```

`<base>` には、1 行目で取得したデフォルトブランチ名を使う。差分が空の場合は、レビュー対象がない旨を伝えて終了する。

### スコープの照合

PR モードでは、`--name-only` で得たファイル数を `changedFiles` と照合する。差分のファイル数が `changedFiles` を超える場合は、他の PR の変更が混ざっている可能性がある。その場合はレビューを始めずに停止し、ユーザーにスコープを確認する。

diff をファイルに保存する場合は、システムプロンプトで案内された scratchpad ディレクトリを使う。書き込みと読み込みには同じ絶対パスを使う。

### WHY（変更の目的）の収集

利用できる情報源から、変更の意図と背景をすべて集める。

- **会話コンテキスト:** これまでのやり取りから変更の意図を読み取る。
- **PR 説明文:** PR モードでは、タイトルと説明文から目的を取得する。
- **コミット履歴:** ローカル差分モードでは、コミットメッセージから目的を推測する。

どの情報源もない場合は、ユーザーに「この変更の目的を教えてください」と確認する。

### 既存レビュースレッドの取得（PR モードのみ）

PR モードでは、PR に付いているインラインのレビュースレッドを取得する。`gh pr view` ではスレッドの解決状態を取れないため、GraphQL を使う。

```bash
gh api graphql -F owner='{owner}' -F name='{repo}' -F number=<PR番号> -f query='
query($owner: String!, $name: String!, $number: Int!) {
  repository(owner: $owner, name: $name) {
    pullRequest(number: $number) {
      reviewThreads(first: 100) {
        totalCount
        nodes {
          isResolved
          isOutdated
          path
          line
          originalLine
          comments(first: 50) {
            nodes { author { login } body createdAt url }
          }
        }
      }
    }
  }
}'
```

- このコマンドは読み取り専用のクエリとしてだけ使う。`mutation` を含むクエリは実行しない。
- `isResolved` が `false` のスレッドを、対応状況の判定対象にする。
- `isResolved` が `true` のスレッドは判定せず、件数だけを数える。
- `totalCount` が 100 を超える場合は、101 件目以降を確認していない旨を結果に明記する。
- 判定対象のスレッドが 0 件なら、Step 3 の既存コメント確認は起動しない。
- 各コメントの日時と比べるため、PR のコミット履歴も取得する（`gh pr view <PR番号> --json commits`）。

### 人間レビュアーの観察の収集

`$ARGUMENTS` や会話コンテキストに、人間レビュアーの観察（気になった箇所や懸念点）が含まれていれば収集する。

- ファイルパス、行番号、懸念の内容だけを抽出してリストにする。
- 観察者の名前は記録も出力もしない。
- 観察がなければ、このステップは飛ばす。

## Step 2: プロジェクト規約文書の検出

リポジトリのルートで、規約として参照できる文書を探す。

- `CLAUDE.md`（ルートと、変更ファイルの親ディレクトリにあるもの）
- `.claude/rules/**/*.md`
- `CONTRIBUTING.md`、`docs/` 配下のコーディング規約やアーキテクチャ文書

見つかった文書のパスをリストにする。1 件以上あれば、Step 3 で規約準拠の観点を起動する。

## Step 3: サブエージェントの並列起動

### 観点ルールの読み込み

このスキルのベースディレクトリにある以下のファイルを Read で読む。

- `references/review-criteria.md`（全観点に共通の基準と出力フォーマット）
- 起動する観点の `references/perspective-*.md`
- 既存コメント確認を起動する場合は `references/existing-comments.md`

サブエージェントはこれらのファイルを直接読めるとは限らない。そのため、ファイルの内容をプロンプトに貼り付けて渡す。

### 起動する観点

Agent ツールで `general-purpose` サブエージェントを、**1 つのメッセージ内で並列に** 起動する。

| 観点 | ルールファイル | 起動条件 | 主に出力するタグ |
| --- | --- | --- | --- |
| ロジック | `perspective-logic.md` | 常時 | `[MUST]` / `[ASK]` |
| セキュリティ | `perspective-security.md` | 常時 | `[MUST]` / `[ASK]` |
| テスト | `perspective-test.md` | 常時 | `[MUST]` / `[ASK]` |
| 改善提案 | `perspective-suggestion.md` | 常時 | `[IMO]` / `[NITS]` |
| 規約準拠 | `perspective-conventions.md` | Step 2 で規約文書が見つかった場合 | `[MUST]` / `[ASK]` |
| 既存コメント確認 | `existing-comments.md` | PR モードで未解決のスレッドがある場合 | 対応状況の判定（タグは付けない） |

既存コメント確認のプロンプトには、差分などに加えて、判定対象のスレッド一覧（パス、行、`isOutdated`、全コメントの本文・日時・URL）と、PR のコミット一覧（ハッシュ、日時、メッセージ）を含める。

観点ごとに出力タグを分けているので、同じ行への重複は起きにくい。ただし、観点の違うタグ（例: ロジックの `[MUST]` と改善提案の `[IMO]`）が同じ行に並ぶことはある。その場合は Step 4 の統合ルールで扱う。

### プロンプトテンプレート

```
あなたは「{観点名}」を担当するコードレビュアーです。読み取り専用で作業し、ファイルを編集しないでください。出力は日本語で行ってください。

## 共通基準
{references/review-criteria.md の内容}

## 担当観点のルール
{references/perspective-{観点}.md の内容}

## プロジェクトの規約文書
以下の文書が存在します。担当観点に関係するものを Read で読み、指摘の根拠として使ってください。
{Step 2 で見つかったパスのリスト（なければ「なし」）}

## 変更の目的（WHY）
{WHY}

## 変更ファイル一覧
{変更ファイル一覧}

## 差分
{差分テキスト全文}

## 人間レビュアーの観察
以下の観察も通常の指摘候補と同じようにゲートチェック（コードの実在確認、今回起因か既存負債かの判定）を行い、ふさわしければタグ付きで出力してください。
{観察リスト（なければこのセクションごと省略）}
```

## Step 4: 結果の統合と表示

### 他観点での気づきの検証

各サブエージェントの結果の末尾に「他観点での気づき」がある場合は、表示の前に以下の順で処理する。

1. すべての気づきを 1 か所に集める。
2. 同じ `ファイル:行番号` への気づきを 1 グループにまとめる。
3. グループ内の推定カテゴリを集め、対応する観点を決める。同じ観点は 1 つにまとめる。
4. 決めた観点のサブエージェントを、1 つのメッセージ内で並列に追加起動する。プロンプトには Step 3 の内容に加えて、気づきの本文と次の指示を含める。「これを自分の観点で検証し、ふさわしければタグ付きの正式な指摘として返してください。観点外と判断した場合は返さなくてかまいません。」
5. 返ってきた指摘を、下の統合ルールに乗せる。何も返ってこなかった気づきは破棄する。

気づきが 0 件なら、このステップは飛ばす。

### 統合ルール

- **重複の統合:** 同じ `ファイル:行番号` への指摘が複数の観点から出た場合は、1 件にまとめる。タグは最も重要度の高いもの（`[MUST]` > `[IMO]` > `[NITS]`）を採用し、他の観点の内容も本文に含める。
- **並び順:** `[MUST]` → `[IMO]` → `[ASK]` → `[NITS]` → `[LGTM]` の順に並べる。
- **空セクションの省略:** 0 件のタグのセクションは出力しない。
- **分類の引き継ぎ:** サブエージェントが付けた `> 今回起因` / `> 既存負債` の分類を維持する。観点によって分類が異なる場合は `> 今回起因` を優先する。
- **既存スレッドとの重複の除外:** 新規の指摘のうち、未解決スレッドと同じファイルの近い行で同じ問題を指しているものは、新規の指摘から外す。外した指摘に新しい観点があれば、そのスレッドの判定理由に書き加える。

### 表示フォーマット

```markdown
## レビュー結果

**対象**: {PR #{番号} {タイトル} | ブランチ {ブランチ名}}
**変更**: {ファイル数} ファイル (+{追加行数}, -{削除行数})

---

### 既存コメントの対応状況

未解決 {N} 件（解決済み {M} 件は判定対象外）

| 判定 | 件数 |
| --- | --- |
| 未対応 | N |
| 対応が不十分 | N |
| 説明の再確認が必要 | N |
| 対応済み（解決してよさそう） | N |

**1. [未対応] コメントの要旨**
📍 `ファイルパス:行番号` ・ {スレッドの URL}

判定の理由（どのコミットやコードを見て判断したかを 1〜3 行で書く）

---

### [MUST] (N件)

**1. [観点] タイトル**
📍 `ファイルパス:行番号`
> 今回起因

本文（3〜5 行を目安に、状況の説明と提案を自然な流れで書く）

---

### [IMO] (N件)

...

### [ASK] (N件)

...

### [NITS] (N件)

...

### [LGTM]

- `ファイルパス` — コメント

---

### 総評

{良い点から始め、改善点があればやわらかく添える。[MUST] がなければ、そのままマージしてよさそうだと伝える。[MUST] があれば、対応が必要である旨を伝える。}
```

### 観察の追加

結果を表示したあとに、ユーザーが「この箇所も確認して」などと観察を追加した場合は、内容から担当の観点を判断してサブエージェントを起動する。結果は既存の出力に統合し、更新した内容を表示する。判断が難しい場合は、Step 3 で起動したすべての観点を再起動する。

## 注意事項

- このスキルはレビュー結果を表示するところまでを担当する。PR へのコメント投稿は行わない。
- レビュー中にコードを編集しない。修正はユーザーから依頼があってから行う。
- トーンは `references/review-criteria.md` の「出力のトーン」に従う。
