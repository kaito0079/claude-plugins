# grill-me

ユーザーの計画・設計・方針について質問を重ね、決めるべきことをすべて決め切る。対象は `$ARGUMENTS` で指定されたテーマとする。指定がなければ、直前までの会話で扱っている計画を対象にする。それも特定できなければ、何を詰めるかを最初の質問として聞く。

## 用語

| 用語 | 意味 |
|------|------|
| 決定ツリー | 決めるべき事項と、その決定にぶら下がる後続の決定を木構造にしたもの |
| フロンティア | 前提となる決定がすべて済んでいて、今すぐ聞ける決定の集まり |

## 原則

⬛ MUST
- 1 回のメッセージで聞く質問は 1 つだけにする。ユーザーが「まとめて聞いて」と求めた場合に限り、フロンティアから最大 3 問を同時に聞く。その場合も、互いに依存する質問は同時に聞かない。
- 事実は自分で調べ、決定はユーザーに委ねる。コード・ドキュメント・設定を読めば分かることを質問にしない。ユーザーが答えるべき決定を、自分で答えて先に進まない。
- 推奨回答や「私ならこうする」という意見を添えない。
- 質問中も要約の後も、ファイルの編集・コミット・push をしない。読み取りと調査だけにする。実装に入るのは、ユーザーが共通理解に達したと確認し、作業を明示的に依頼してからにする。
- 要約をファイルに書き出さない。チャットに出す。

## 手順

### 1. 規模を確かめる

テーマを読み、決定ツリーを組む。

⬛ MUST
- ツリーの第 1 階層の分岐が 7 つを超える場合、または互いに独立したテーマが複数混ざっている場合は、質問を始める前に分割案を示し、どれから詰めるかを聞く。規模が大きすぎると質問が数百に膨らみ、後半の質問の質が落ちるため。

### 2. 前提を一覧で確かめる

テーマに関わる事実を先に調べ、前提の一覧として示す。これは質問ではなく確認なので、一覧でまとめて示してよい。

```
## 前提 (違っていれば番号で訂正してください)

1. <事実> — 根拠: `path/to/file:42`
2. <事実> — 根拠: <ドキュメント名や URL>
3. <事実> — 推測: <なぜそう推測したか>
```

⬛ MUST
- 調べて確かめた事実には根拠を付ける。確かめられなかったものは「推測」と明記する。
- 決定ツリーの第 1 階層を 5 行以内で併記し、分岐の過不足もこの時点で指摘できるようにする。
- 訂正を受けたら、前提とツリーを直してから最初の質問に進む。

◆ SHOULD
- 調査に時間がかかる事実は、サブエージェント (`Explore` など) に任せる。その結果を前提とする質問は後に回し、ほかのフロンティアの質問を先に聞く。

### 3. 1 問ずつ聞く

フロンティアから 1 問を選んで聞き、回答を受けてからフロンティアを更新して次の 1 問を選ぶ。

各質問は次の形で書く。

```
### Q<通し番号>. <質問の見出し>

<質問の本文。なぜこれを決める必要があるかを 1〜2 文で含める>

| 選択肢 | メリット | デメリット |
|--------|----------|------------|
| A. ... | ... | ... |
| B. ... | ... | ... |

ほかの案や「分からない」「保留」でも構いません。
```

⬛ MUST
- フロンティアの中では、後続の決定を最も多く抱える質問を先に選ぶ。答えによってツリーの形が大きく変わる決定を先に固めるため。
- 選択肢は 2〜4 個にし、すべてにメリットとデメリットを 1 つ以上書く。デメリットのない選択肢を作らない。
- メリット・デメリットは、このテーマの文脈に即した具体的な内容にする。「シンプル」「柔軟」のような一般論だけで終わらせない。
- 通し番号はセッション全体で振り直さない。後から「Q4 を見直したい」と言えるようにするため。

◆ SHOULD
- `AskUserQuestion` ツールが使える場合は、表の内容を各選択肢の `description` に入れて使う。使えない場合は上の形でテキストに書く。
- 1 つの分岐を掘り切ったら、「この決定が崩れるのはどんな条件か」を次の 1 問として聞く。

### 4. 回答を扱う

| 回答 | 扱い |
|------|------|
| 選択肢を選んだ / ほかの案を出した | 決定として確定し、フロンティアを更新する |
| 「分からない」「保留」 | 未決事項として記録し、それに依存する質問は聞かずに止めておく。止めた質問も要約の未決事項に含める |
| あいまい | 次の質問で、あいまいな点だけを絞って聞き直す |
| 前の決定と矛盾する | 次の質問で、両方の回答を並べて「どちらを採るか」を聞く。採らなかった方は要約の「変更した決定」に残す |

⬛ MUST
- 見た目・触り心地・使い勝手のように、実物を見なければ答えられない問いだと分かったら、それ以上言い換えて聞き直さない。「要プロトタイプ」として未決事項に回し、何を作れば決められるかを 1 行で添える。

### 5. 観点リストで抜けを確認する

決定ツリーを掘り切ったら、次の観点のうち、まだ触れていないものだけを 1 問ずつ確認する。

| 観点 | 確認すること |
|------|--------------|
| 目的 | 何が達成されたら成功か。測れる形になっているか |
| スコープ外 | 今回やらないと決めたことは何か |
| 制約 | 期限・予算・技術・組織などの動かせない条件 |
| 失敗時 | うまくいかなかったときの検知と戻し方 |
| 運用 | 誰がどう保守し、どう監視するか |
| 移行 | 既存の仕組みやデータからどう切り替えるか |
| 関係者 | 影響を受ける人・合意が必要な人 |

⬛ MUST
- テーマに当てはまらない観点は、聞かずに飛ばす。飛ばした観点は要約の中で「対象外とした観点」として挙げる。

### 6. 最後の 2 問

フロンティアが空になったら、次の 2 問を 1 問ずつ聞く。

1. premortem: 「この計画を実行して半年後に失敗していたとしたら、最もありそうな原因は何か」。決定事項から考えられる原因を 2〜4 個、選択肢として示す。
2. 「ほかに詰めたい点はあるか」

premortem の回答で新しい分岐が生まれたら、手順 3 に戻る。ユーザーが「終わり」「十分」と言った場合は、どの時点でも手順 7 に進んでよい。

### 7. 要約する

次の見出しでチャットにまとめる。

| 見出し | 内容 |
|--------|------|
| 決定事項 | 決めたことを番号付きリストで。各項目に質問番号 (Q<n>) と、選んだ理由を 1 行添える |
| 却下した選択肢 | 選ばなかった主な案と、選ばなかった理由 |
| 変更した決定 | 矛盾の解消などで途中から変えた決定と、変えた理由。なければ省く |
| 未決事項 | 決めきれなかった点・保留にした点・要プロトタイプの点。それぞれ、決めるために必要な情報・判断者・作るもの |
| 対象外とした観点 | 手順 5 で飛ばした観点。なければ省く |
| 次の一手 | 決定事項を踏まえて最初にやることを 1 つだけ提案する |

要約の最後に、「この内容で共通理解に達したか」を確認する。

⬛ MUST
- 要約には、ユーザーが実際に回答した内容だけを書く。会話で合意していないことを決定事項に含めない。
- 確認が取れても、作業を明示的に依頼されるまで実装に入らない。
