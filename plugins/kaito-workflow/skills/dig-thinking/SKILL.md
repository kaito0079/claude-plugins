# 考えの深掘り

ユーザーが下した判断や、持っている考えを、質問を重ねて言語化する。目的は、ユーザーがいない場面でも、他のメンバーやエージェントが同じ判断にたどり着けるようにすることである。

計画や設計を詰めるインタビューとは、対象が異なる。このスキルが掘るのは「何を作るか」ではなく、「この人はなぜそう判断するのか」である。

## ゴール

次の項目がすべて埋まった判断メモを、ユーザーが「自分の考えとして正しい」と認めた状態で提示する。

| 項目 | 内容 |
| --- | --- |
| 原則 | 判断基準を 1 文で言い切ったもの |
| 理由 | その原則を持つに至った理由。何を守るため、何を避けるためか |
| 適用範囲 | どんな状況でこの原則を使うか |
| 例外と境界 | この原則を使わない状況と、その線引き |
| 優先順位 | 他の原則とぶつかったときに、どちらを優先するか |
| 具体例 | 原則を適用した例。案件固有の事情を取り除いたもの |
| 未解決の問い | まだ答えが出ていない点 |

## 進め方

### Step 1: 起点を決める

`$ARGUMENTS` や会話の中に、深掘りの対象があればそれを使う。なければ、次のように聞く。

> 最近、迷った判断や、人に説明しづらかった判断はありますか。

抽象的なテーマ（例:「品質について」）しかない場合は、そのテーマに関する**最近の具体的な出来事**を 1 つ挙げてもらってから始める。抽象論から始めると、建前の答えになりやすいためである。

### Step 2: ラウンド制で質問する

1 ラウンドに 1〜3 問を出し、ユーザーの回答を待ってから次のラウンドに進む。答えが前の質問に依存する質問は、同じラウンドに入れない。

各質問には、**Claude の仮説**を添える。ゼロから言葉にするより、仮説を直すほうが、本人の考えを引き出しやすいためである。

```
❓ **Q1** - **質問の見出し**: 質問の本文

➡️ 仮説: あなたの判断は「〜」と言い換えられそうです。合っていますか。

---

❓ **Q2** - ...
```

### Step 3: 角度を変えて掘る

次の角度を、回答の状況に合わせて使い分ける。すべてを順番に使う必要はない。

| 角度 | 目的 | 質問の例 |
| --- | --- | --- |
| 具体化 | 建前ではなく実際の行動を引き出す | 「そのとき、実際に何をしましたか。何をしませんでしたか。」 |
| なぜの掘り下げ | 行動の奥にある価値観にたどり着く | 「それをしないと、何が困りますか。」を 2〜3 回繰り返す |
| 反例 | 原則の境界を見つける | 「同じ状況で、逆の判断をするとしたら、何が違うときですか。」 |
| 衝突 | 優先順位を決める | 「スピードと品質がぶつかったら、どちらを取りますか。どこまでなら妥協しますか。」 |
| 他者視点 | 他の人が再現できる形にする | 「新しく入ったメンバーが同じ場面に立ったら、何を見て判断すればよいですか。」 |
| 汎用化 | 案件固有の事情を外しても成り立つか確かめる | 「この案件でなくても、同じ判断をしますか。」 |

### Step 4: 矛盾を指摘する

次のような食い違いに気づいたら、その場で指摘し、どちらが本心かを聞く。

- 今回の回答と、同じ会話の前半の回答の食い違い
- 回答と、既存の判断基準ファイルやスキルのルールとの食い違い
- 回答と、実際の行動（コード、コミット、PR など）との食い違い

矛盾は、原則に例外や条件が隠れているサインである。どちらかを誤りと決めつけず、両方が成り立つ条件を探す。

### Step 5: 判断メモにまとめる

ゴールの項目がすべて埋まったら、判断メモを提示する。1 回の深掘りで原則が複数出てきた場合は、原則ごとにメモを分ける。

```markdown
## 原則: {1 文で言い切る}

**理由:** {何を守るため、何を避けるためか}

**適用範囲:** {どんな状況で使うか}

**例外と境界:** {使わない状況と、その線引き}

**優先順位:** {〜より優先する / 〜には譲る}

**具体例:** {汎用化した例}

**未解決の問い:** {あれば}
```

提示したら、ユーザーに「自分の考えとして正しいか」を確認する。修正があれば反映し、再度確認する。

### Step 6: 保存する

保存先は、次の順で決める。

1. ユーザーが保存先を指定した場合は、そこに書く。
2. 作業ディレクトリに判断基準ファイル（`PRINCIPLES.md` など）がある場合は、追記案を提示し、承認を得てから書く。既存の原則と重複や矛盾がある場合は、統合案も示す。
3. どちらでもない場合は、判断メモを表示するだけで終える。ファイルは作らない。

## ルール

⬛ MUST

- 判断はユーザーのものである。Claude の価値観で、ユーザーの判断を正したり評価したりしない。
- 仮説は確認のための叩き台として出す。ユーザーが否定した仮説を、言い方を変えて押し付けない。
- コード、コミット、ファイルなど、調べれば分かる事実はユーザーに聞かずに自分で調べる。ユーザーに聞くのは、判断と理由だけにする。
- 公開する場所に保存する場合は、社名、顧客名、案件名、社内システム名などの固有の情報を取り除く。取り除くと意味が変わる場合は、保存前にユーザーに確認する。
- ユーザーが確認する前に、判断メモをファイルに書き込まない。

◆ SHOULD

- 1 回の深掘りは、1 つの判断か 1 つのテーマに絞る。広がりすぎた場合は、残りを「未解決の問い」に回し、次回の起点にする。
- ユーザーの言葉をそのまま使う。Claude が言い換えた言葉で原則を書くと、本人が読んだときに違和感が出る。
- 「場合による」という回答には、「どんな場合に、どちらになりますか」と聞き返し、条件を言葉にする。

○ NICE TO HAVE

- 深掘りの途中で、別の原則につながりそうな話題が出たら、メモの末尾に「次に掘る候補」として残す。

## 終わり方

次のどちらかで終える。

- ゴールの項目がすべて埋まり、ユーザーが判断メモを承認した。
- ユーザーが中断を求めた。この場合は、そこまでの内容を、埋まっていない項目を明示した判断メモとして提示する。
